# Package Binary unmatched-point ceiling

The approved default is enabled at 180,000 unmatched points on each leg for every current package, including Starter, Silver and Gold. The ceiling applies to remaining point volume, not lifetime points, member count, pairs already earned, inventory, or wallet balance. Both legs use the same limit so a change in which side is stronger needs no special handling.

Settlement first applies the current daily/session allowance and plans matching. It then rejects only the new source volume that would leave its leg over the point ceiling. For example, 179,700 stored points plus a 600-point source with no possible pair accepts 300 and flushes 300. A full strong leg does not prevent opposite-leg volume from matching; consuming 600 stored points creates space for subsequent incoming volume while session allowance remains.

Session closure takes precedence: when the session/daily allowance is exhausted, all new source points are flushed even if balance space remains. The event records total flushed points, session/daily flushed points, and balance-ceiling flushed points separately. Their sum is verified by the database; rejected volume never enters a point lot, becomes cash income, or advances the bottle counter. Matching consumes the existing FIFO lots and uses the existing cash/product entitlement calculation and replay protections.

Existing balances above a newly enabled or reduced limit are preserved. They cannot accept additional unmatched volume on that leg until pairing or the existing expiry process creates room. There is no retroactive deletion or overnight wipe of stored points, and turning the ceiling off does not restore earlier flushed sources. This grandfathering is deliberate; the ceiling constrains new volume rather than rewriting immutable historical credits or point lots.

Admin Settings → Package Binary cap policy adds an on/off control and maximum points per leg for each package. Enabled limits must be at least one pair's point threshold; limits must be positive whole PostgreSQL integers. Disabling preserves the saved numeric limit for later re-enabling. Changes require the active owner's Security PIN, same-origin request, and latest cap-version ID. They take effect at a future Philippine midnight, never by resetting current usage.

The API saves the cap-mode version, independent carryover-policy version, and audit evidence in one locked transaction. Existing future cap-mode schedules inherit the most recent effective carryover version rather than silently switching the ceiling off. Both effective policy references and the balance limit are captured on new pair events. Versions are immutable, owner-attributed, future-dated, and require their matching deferred audit record. The bootstrap migration seeds the approved default with a system audit entry; new packages receive their own default version and audit evidence through a restricted trigger function.

Migration: `20261102100000_package_binary_unmatched_balance_cap`, after `20261102090000_configurable_package_binary_cap_policy`. It adds records and nullable event snapshots without changing old balances, lots, commissions, rewards, or cap usage. Deploy the matching application before processing transactions that can exceed the new ceiling. Runtime credentials require the new table/sequence permissions and must not own financial objects or execute the initialization trigger function directly; the existing runtime-role verifier covers that function and table.

Validation includes both-leg partial admission, full-leg rejection, matching before the ceiling, reopening space, session precedence, separately classified flush points, on/off and limit scheduling, source snapshot forgery, pre-existing excess, immutable histories, new-package initialization, point-lot reconciliation, signed-integer boundaries, and 10,000 generated planner conservation checks. The standard 5,000-member release simulation now includes the default ceiling. These checks establish rule behavior, not financial sustainability.
