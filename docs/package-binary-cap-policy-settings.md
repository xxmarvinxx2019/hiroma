# Configurable Package Binary cap policy

Admin Settings now provides a per-package cap-policy editor. Daily anytime uses one daily allowance with no session cutoff. Two sessions uses a first-session allowance, a Philippine-time cutoff, and a second allowance equal to the daily maximum minus the first. Both modes reject incoming source points after the applicable cap, preserve existing carryover, and count cash and bottle pairs together. The same editor now schedules the independent unmatched-balance policy; see package-binary-unmatched-cap.md.

The initial migration preserves each package's current enabled flag and limits, with the existing 13:00 two-session split (a historical one-pair daily limit is represented as daily anytime). No usage, commissions, bottles, or point lots are rewritten. New packages start with the existing enabled 10/day default.

Saving requires the active owner administrator, the existing persistent Security PIN verifier, a same-origin request, and the latest policy-version ID. A stale form returns 409. Each insert and before/after audit entry commit together under the settlement policy lock. Versions cannot be edited, deleted, or truncated. Only future Philippine effective dates are accepted. Saving a corrected version for the same effective date supersedes that date's previous version without deleting its history; later scheduled dates remain in force.

Activation needs no scheduled worker: both the application and database validator call `package_binary_cap_state` using transaction start time. The latest version whose effective date is on or before that transaction's Philippine date determines its allowance. A delayed transaction keeps its earlier day's policy. Mode and cutoff changes never reset daily usage. Historical events retain their original snapshots; new events record policy reference, mode, cutoff, and session. Daily anytime uses session marker 0. Unknown historical usage is conservatively included in applicable allowance.

The Packages form links to Admin Settings rather than editing cap fields directly. Package update endpoints no longer accept immediate cap changes, and a database trigger rejects legacy cap-field edits. New scheduled policies keep caps enabled. Limits are whole numbers up to 10,000; two-session policies require positive allowances totaling the daily limit and a cutoff from 00:01 to 23:59. No change to the current daily limit is made merely by opening the editor.

Apply migration `20261102090000_configurable_package_binary_cap_policy` after the daily-usage and two-session migrations, with the matching application. A non-owner runtime role needs SELECT/INSERT on the policy table, USAGE on its revision sequence, and SELECT on its dependencies; retain the existing restrictions on ownership, trigger creation, truncation, and schema manipulation. Do not schedule a future policy before the matching application is deployed. The migration's seeded policy preserves the current behavior for older code; a later changed policy requires the new application.

Validation includes daily-anytime morning exhaustion, configurable session boundaries, version supersession, effective-day selection, delayed prior-day transactions, immutable policy history, owner/audit requirements, legacy-write rejection, and existing cap/reward/point-lot regression tests. No source retry can move an already-settled event into a newly scheduled policy or recreate earned rewards.
