# Lifetime reseller account limit

The approved rule is seven total accounts for matching full legal name (including middle names) and birthday, across every City/Branch and ID type. Active, suspended and inactive accounts all count. Suffix and harmless formatting differences do not create another identity. ID-document hashes are also permanently bound to the enrolled identity.

The existing duplicate popup remains. Confirming the same person counts all matching historical accounts. The former different-person override is removed from both registration screens and rejected on the server. Genuine people with identical legal names and birthdays require identity review; this change deliberately supplies no branch override or automated approval workflow.

Migration `20261103090000_lifetime_person_account_limit` creates immutable lifetime membership and ID-alias records and an atomic person counter limited to seven. A deferred database trigger reads the final user row, supporting registration's create-then-write-birthday transaction. It enforces direct inserts and role/identity changes as well as application registrations. Failed or competing transactions roll back both enrollment and financial work. Deactivation/reactivation no longer releases or reclaims capacity. Existing memberships cannot be deleted through account deletion, reassigned by name/birthday edits, or reset by table deletion/truncation using ordinary runtime privileges. Financial runtime verification now covers these tables and the restricted trigger function.

Apply the migration with an owner deployment connection and deploy matching application code. It intentionally aborts if historical resellers have incomplete identity data, more than seven matching identities, or one ID attached to inconsistent legal details. Reconcile these cases before activation; do not delete financial accounts to force migration success. No existing commissions, points, rewards or wallets are changed by this migration. Identity counters are reconciled including inactive accounts, with max_allowed fixed to seven. The migration has not been applied to the shared database by this task.

Limits: this is deterministic legal-name/birthday enforcement, not proof of a real unique human. Fabricated or altered names/birthdays submitted under different IDs still require credible identity verification to detect. No biometric or government-ID verification is added. Legacy full names must be reviewed for consistency with structured first/middle/last names before activation. Existing identity corrections are deliberately blocked once enrolled pending a separately audited correction workflow. Database owners retain the power to alter protections.

Validation uses disposable PostgreSQL schemas, including 20 concurrent registrations with different IDs and mixed statuses (seven succeed), eighth-account rejection after deactivation, middle-name differentiation, rollback, staged registration, ID conflicts and registry tamper attempts. This task does not push, merge or activate the migration.
