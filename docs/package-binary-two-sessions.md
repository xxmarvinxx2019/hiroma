# Package Binary: two daily sessions

Approved policy: all current packages have a 10-pair daily allowance, split into 5 pairs before 13:00 and 5 pairs from 13:00, Asia/Manila. The first session begins at midnight. Unused session allowance never transfers. Cash and bottle pairs both consume allowance. Product Binary and direct-referral rules are unchanged.

After an account consumes its session allowance, all new incoming Package Binary points on either leg are rejected, including unmatched points. They are recorded as flushed source volume and never become carryover. If one source transaction reaches the last available pair, only the new points needed to complete that pair are accepted; its surplus is flushed. Valid pre-existing unmatched carryover remains subject to its existing expiry. Other ancestors are evaluated independently, so one capped ancestor does not block the entire cascade.

The pairing day and session use database transaction start time in Philippine time. A transaction begun before 13:00 belongs to the first session even if it commits later. A request begun before midnight belongs to that earlier day. Retries recover the original financial result; they do not move an already-settled source into a new session. This is processing time, not the time a customer verbally ordered or paid outside the application.

Daily usage remains authoritative in `binary_daily_cap_usage`. Session usage is calculated from immutable pair events under the same member locks used for settlement. The database independently verifies exact accepted/flushed source volume, opening and closing points, daily and session allowance, cash/bottle partition, and closing session usage. Only accepted source volume creates a point lot. A deferred check reconciles credited lots, consumed lots, and remaining balances with each event. The point-lot deferred validator reads final row state so a lot can be created and immediately consumed in one transaction. Source uniqueness, commission keys, and atomic rollback still apply. A browser clock or submitted session/count cannot grant allowance.

Each pair event preserves original source points, flushed source points, database-authored session, and session opening/closing counts. Accepted points equal original minus flushed points. Rejected points do not become a fictional peso commission or increase Hiroma's cash balance. They do not advance the cumulative product-reward counter. The reseller dashboard exposes paginated own-account points history and current allowance. Admin Binary Commission audit details and CSV include the same flush/session fields; its cap filter includes rejected source volume.

Migration `20261101090000_package_binary_two_sessions` sets every existing package's enabled daily limit to 10, records the prior package settings and the new policy in `audit_logs`, and adds fields without rewriting old events, earned bottles, commissions, or point lots. Existing same-day usage is retained. Historical events are assigned to sessions for calculation using their recorded timestamps, without changing the rows. Any dated usage not covered by events is conservatively charged to either queried session rather than granting extra slots. Consequently a mid-day cutover may leave less than five afternoon slots; no reset is promised.

The existing admin package configuration remains editable. Future daily limits split as integer half before 13:00 and the remainder afterward, each bounded by the daily limit. Disabling the package cap deliberately disables both limits. Cap configuration saves and package changes now commit atomically and record the acting administrator and before/after cap values. Changing a limit does not erase usage. The approved rollout itself enables all current package caps at 10.

Deployment: quiesce registration/upgrade settlement, apply the prior daily-usage migration and this migration, deploy the matching application, then resume. Older application code will fail validation under the new policy rather than grant excess points. Use separate non-owner runtime credentials and run the financial runtime-role verifier. Local application and the configured database are distinct from a verified production deployment.

Validation covers cap overshoot, both-leg rejection, 12:59:59/13:00 boundaries, next-day reset, out-of-order sessions, concurrency for the final slot, rollback, source replay, cache tampering, inactive accounts, unused morning allowance, and cumulative bottle rewards. Disposable-schema tests use production validators and production planning/usage helpers with a test-only clock substitution. They are not a load benchmark or proof of long-term profitability.
